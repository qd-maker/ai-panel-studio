# AI Panel Studio 产品需求文档（PRD）

本文档定义 MVP 的范围、用户故事、讨论推进规则和验收标准。数据模型见 [ER.md](ER.md)，接口契约见 [API.md](API.md)。作业原文见 [assignment.md](assignment.md)。

## 产品范围

AI Panel Studio 是一个本地运行的 Web 应用。用户输入话题和专家人数，系统用大模型生成一位主持人和一组专家。用户确认阵容后，系统在后台推进一场圆桌讨论，浏览器通过 SSE 实时显示发言、专家状态、共识与分歧，最后由主持人做自然语言总结。

用户在 MVP 中只做三件事：发起讨论、确认阵容、旁观讨论。用户不参与发言。

### 不做的事情

- 用户账号、登录和权限。本地单用户使用。
- 用户插话或向专家提问。
- 讨论录制导出、回放进度条。
- 多实例部署。讨论的后台任务跑在单个后端进程内。
- 发言的逐字流式输出。后端生成完整一句后再推送，前端用打字机效果呈现。

### 关键参数

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 话题长度 | 5～200 字 | 去掉首尾空白后计算 |
| 专家人数 | 2～6 人，默认 4 人 | 不含主持人 |
| 单条发言 | 最多 2 句，最多 120 字 | 适用于主持人和专家的所有发言，总结除外 |
| 专家发言轮数上限 | 12 轮 | 达到后进入总结 |
| 主持人介入间隔 | 每 3 条专家发言 | 另有无人想发言时立即介入 |
| 共识与分歧提炼频率 | 每新增 2 条发言 | 讨论进行中持续运行 |
| 同时运行的讨论数 | 最多 3 场 | 控制模型调用成本，超出返回 429 |
| 发言间隔 | 1.5 s～3 s | 留出时间显示“准备发言”状态，营造现场节奏 |
| 公开思考摘要 | 最多 60 字 | 由模型单独输出的字段 |
| 当前关注点 | 最多 20 字 | 由模型单独输出的字段 |
| 总结 | 3～6 句，最多 600 字 | 纯文本，可分段 |

## 用户故事

验收标准使用 Given/When/Then 格式。编号 AC-x.y 在测试代码中引用。

### US-1 浏览首页讨论列表

作为旁观者，我想在首页看到正在进行的讨论，以便选一场进去看。

- **AC-1.1** Given 系统中有 2 场 `running` 和 1 场 `done` 的讨论，When 打开首页，Then“进行中”分组显示这 2 场，每场显示话题、嘉宾色块、已发言条数和开始时间。
- **AC-1.2** Given 数据库已导入 5 条预设样例，When 打开首页，Then“待开始”分组显示这 5 场，状态为 `lineup_ready`。
- **AC-1.3** Given 系统中有 `draft` 状态的讨论，When 打开首页，Then 列表里没有这场讨论。
- **AC-1.4** Given 首页已打开，When 另一场讨论从 `running` 变成 `done`，Then 刷新列表后它出现在“已结束”分组。

### US-2 中途加入一场讨论

作为旁观者，我想进入一场已经开始的讨论，并看到之前的全部内容。

- **AC-2.1** Given 一场讨论已产生 8 条发言、3 条共识与分歧，When 我进入演播厅，Then 页面先显示这 8 条发言、3 条条目和每位专家的当前状态，再继续接收新内容。
- **AC-2.2** Given 我进入演播厅时，后端正好在写第 9 条发言，When 页面加载完成，Then 第 9 条发言恰好出现一次。
- **AC-2.3** Given 我在看讨论时网络断开 10 s，When 浏览器自动重连，Then 断线期间的发言按顺序补齐，没有重复，也没有缺失。

### US-3 发起讨论并生成阵容

作为用户，我想输入话题和人数，得到一组立场不同的嘉宾。

- **AC-3.1** Given 话题为“AI 会取代初级程序员吗”、人数为 4，When 提交，Then 返回 1 位主持人和 4 位专家，讨论状态为 `lineup_ready`。
- **AC-3.2** Given 生成的阵容，When 查看每位嘉宾，Then 每人都有非空的姓名、职业、Title、立场和颜色，5 个人的颜色互不相同。
- **AC-3.3** Given 生成的阵容，When 比较 4 位专家的立场，Then 至少有 1 位专家的立场与其他人相对。生成提示词要求立场覆盖正反两方，后端校验立场字段两两不同。
- **AC-3.4** Given 话题少于 5 字或人数为 7，When 提交，Then 返回 422，错误码为 `VALIDATION_ERROR`，不调用模型。
- **AC-3.5** Given 模型调用重试后仍然失败，When 提交，Then 返回 502，响应里带讨论 id，讨论停在 `draft`，用户可以调用“重新生成阵容”重试。

### US-4 重新生成阵容

- **AC-4.1** Given 讨论处于 `lineup_ready`，When 请求重新生成，Then 旧嘉宾全部被替换，返回新阵容，状态仍为 `lineup_ready`。
- **AC-4.2** Given 讨论处于 `running`，When 请求重新生成，Then 返回 409，错误码为 `INVALID_STATE_TRANSITION`，嘉宾不变。
- **AC-4.3** Given 一次重新生成正在进行，When 用户再次请求重新生成或请求开始，Then 立即返回 409，错误码为 `LINEUP_GENERATING`；第一次生成完成后，讨论只有一套阵容。

### US-5 确认阵容并开始

- **AC-5.1** Given 讨论处于 `lineup_ready`，When 确认开始，Then 返回 202，状态变为 `running`，5 s 内出现主持人的开场发言。
- **AC-5.2** Given 已有 3 场讨论处于 `running`，When 再开始一场，Then 返回 429，错误码为 `TOO_MANY_RUNNING`，状态仍为 `lineup_ready`。
- **AC-5.3** Given 讨论已经在 `running`，When 再次请求开始，Then 返回 409。

### US-6 主持人主持讨论

- **AC-6.1** Given 讨论开始，When 查看第 1 条发言，Then 发言人是主持人，`act` 为 `opening`。
- **AC-6.2** Given 已连续出现 3 条专家发言，When 推进下一轮，Then 下一条发言来自主持人，`act` 为 `question`（追问某位专家）或 `bridge`（串联观点）。
- **AC-6.3** Given 主持人追问了专家 X，When 推进下一轮，Then 下一条发言来自专家 X，`act` 为 `answer`。

### US-7 专家自主发言

- **AC-7.1** Given 每轮 4 位专家各自给出发言意图和紧迫度，When 调度器选人，Then 选中得分最高的专家，跟座位顺序无关。
- **AC-7.2** Given 专家 A 刚发完言，When 下一轮选人，Then 不选 A，除非 A 正在回答主持人的追问。
- **AC-7.3** Given 每条专家发言，When 检查 `act`，Then 取值属于 `point`、`supplement`、`rebut`、`answer` 之一，`rebut` 和 `supplement` 带 `reply_to_utterance_id`。
- **AC-7.4** Given 本轮没有专家想发言，When 推进，Then 主持人追问发言次数最少的专家。

### US-8 专家状态小窗

- **AC-8.1** Given 讨论进行中，When 观察任意一位专家的小窗，Then 状态在 `idle`（待机）、`preparing`（准备发言）、`speaking`（发言中）之间变化，并显示当前关注点和公开思考摘要。
- **AC-8.2** Given 专家想在本轮发言，When 调度器尚未选人，Then 该专家小窗显示“准备发言”。
- **AC-8.3** Given 专家被选中，When 后端开始生成发言，Then 小窗显示“发言中”；发言推送后，状态回到“待机”。

### US-9 实时共识与分歧

- **AC-9.1** Given 讨论进行中，When 新增第 2 条发言后完成一次提炼，Then 共识与分歧区域出现条目或更新已有条目，不必等讨论结束。
- **AC-9.2** Given 每条共识或分歧，When 查看，Then 显示内容、认同者色块、反对者色块和状态（初现、确认、已化解、已推翻）。
- **AC-9.3** Given 模型提炼出的条目引用了不存在的发言 id，When 后端校验，Then 丢弃这一条，其余条目照常写入。

### US-10 现场 Transcript

- **AC-10.1** Given 一条发言，When 显示在 Transcript，Then 带发言人姓名、职业或 Title，色块颜色与该嘉宾的专属颜色一致。
- **AC-10.2** Given 新发言到达，When 用户停留在 Transcript 底部，Then 自动滚动到最新一条；用户向上翻阅时不强制滚动，显示“有新发言”按钮。

### US-11 总结

- **AC-11.1** Given 专家发言达到 12 轮，When 推进，Then 状态变为 `summarizing`，主持人说一句收尾，然后推送总结，状态变为 `done`。
- **AC-11.2** Given 总结生成重试后仍失败，When 进入 `done`，Then 后端用已有的共识与分歧拼出一段中文总结，`summary_source` 为 `fallback`。

### US-12 中止讨论

- **AC-12.1** Given 讨论处于 `running`，When 用户点击“结束讨论”，Then 后台任务停止，状态变为 `aborted`，已有发言保留可看。
- **AC-12.2** Given 后端进程重启，When 启动完成，Then 原来处于 `running` 和 `summarizing` 的讨论状态变为 `aborted`，原因写明“服务重启”。

## 讨论推进规则

后端为每场讨论运行一个独立的后台任务，按下面的循环推进。调度器（第 2 步）写成纯函数，输入意图列表和历史，输出被选中的人，便于单元测试。

1. **收集意图**：一次模型调用拿到全部专家的意图。每位专家的意图包含是否想发言、取得发言权的方式（举手或抢答）、发言性质（新观点、补充、反驳、回答）、针对谁、紧迫度（1～5）、当前关注点和公开思考摘要。意图写入 `internal` 事件，关注点和摘要更新到专家小窗。
2. **选人**：
   - 主持人刚追问了某位专家，这位专家直接发言。
   - 其余情况，从想发言的专家里排除上一位发言人，按得分取最高者。得分 = 紧迫度 + 抢答且针对上一位发言人时加 2 + 本场发言次数最少时加 1。同分时，发言次数少的优先，再按意图里的顺序。
   - 没有候选人时，主持人介入。
3. **主持人介入**：连续 3 条专家发言后，或第 2 步没有候选人时，主持人发言，可以追问某位专家，也可以串联前面的观点。
4. **生成发言**：被选中的人状态变为 `speaking`，模型生成 1～2 句。后端校验长度，超过 2 句时截到第 2 个句末标点。
5. **提炼共识与分歧**：每新增 2 条发言，调用一次提炼。输入是现有条目和新发言，输出是新建、更新、改状态三种操作，每条操作都要引用发言 id。
6. **结束**：专家发言达到 12 轮，进入总结。

“举手”“抢答”描述的是专家怎样拿到发言权，只出现在 `internal` 事件里。“补充”“反驳”描述的是发言本身的性质，作为发言的 `act` 字段公开显示。

## 验收标准：禁止项

作业中每一条“禁止”或“不得”都对应下表中的一条可测试标准。TDD 和 E2E 阶段的测试用例按编号覆盖。

| 编号 | 作业原文要求 | 可测试的验收标准 | 验证方式 |
| --- | --- | --- | --- |
| P-01 | 不展示真实的隐藏 chain-of-thought | 假模型在每次回复里附带 `reasoning_content: "SECRET_COT"`。跑完一场讨论后，所有 API 响应、SSE 数据和页面 DOM 中都找不到 `SECRET_COT`，也没有名为 `reasoning` 或 `reasoning_content` 的字段。小窗只显示意图里的 `public_thought` 字段 | 集成测试 + E2E |
| P-02 | 不允许机械式轮流发言 | 给定 4 位专家的意图，紧迫度排序为座位 3、1、4、2，调度器依次选出座位 3、1、4、2。用固定种子的假模型跑满 12 轮，专家发言序列与按座位轮流的序列不同 | 单元测试 |
| P-03 | 专家每次发言控制在 1–2 句 | 所有发言（总结除外）的句末标点不超过 2 个，长度不超过 120 字。模型返回 4 句时，后端截断为 2 句后再保存 | 单元测试 |
| P-04 | 共识与分歧不等到讨论结束后才生成 | 在事件流中，第一个 `insight` 事件的 id 小于状态变为 `summarizing` 的事件 id，并且出现在第 4 条发言之前 | 集成测试 |
| P-05 | Transcript 不显示“举手”等内部事件 | SSE 流和详情接口中只出现 `public` 事件。E2E 中 Transcript 区域的条目数等于发言条数，文本中不出现“举手”“抢答” | 集成测试 + E2E |
| P-06 | 禁止将 JSON 原文显示到页面上 | 假模型把总结返回成 JSON 字符串时，后端提取出其中的自然语言字段，提取不到就用兜底总结。保存的 `summary` 用 `json.loads` 解析会失败，并且不以 `{` 或 `[` 开头。E2E 中总结区域文本不含 `{"` | 单元测试 + E2E |
| P-07 | API Key 只能放在后端，不得暴露到浏览器 | 前端构建产物和所有 API 响应中找不到 Key 的值。前端代码里没有任何 `VITE_` 开头且含 `KEY` 的变量。浏览器网络面板里没有发往模型服务商域名的请求 | 自动化检查 + E2E |
| P-08 | 多场讨论必须互相隔离 | 同时运行讨论 A 和 B，A 的 SSE 流里每条数据的 `discussion_id` 都等于 A；A 的详情接口里没有 B 的发言、条目和嘉宾 | 集成测试 |
| P-09 | 中文 UI，响应式，不依赖整页滚动 | 在 2560×1440、1440×900、390×844 三种视口下，`document.documentElement.scrollHeight` 不大于视口高度；Transcript、专家区、共识与分歧区各自可以滚动；界面文字全部为中文（专有名词除外） | E2E |

## 非功能要求

- **成本**：每场讨论约 45 次模型调用：约 19 次发言生成、约 17 次意图收集、约 9 次共识与分歧提炼。测试和 E2E 全部使用假模型，不消耗额度。
- **可靠性**：每次模型调用超时 30 s，失败重试 2 次。连续 3 轮发言生成失败时，讨论状态变为 `failed`。
- **可观测**：每次模型调用的耗时、token 用量和失败原因写入 `internal` 事件，方便排查。
